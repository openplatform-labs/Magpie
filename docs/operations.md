# 로컬 운영 및 복구

## 실행 및 마이그레이션

공급자 그룹 이관(0027)은 기존 TypeSafe 연결을 판단 전용으로, 그 밖의 연결을 범용으로 설정합니다. 기존 모델·키·복수 작업 설정은 유지합니다. 신규 모델에는 작업 하나만 등록할 수 있고 전용 공급자 연결은 해당 작업만 허용합니다. 공급자 그룹은 관리 화면이나 `PUT /admin/providers/{id}/model-group`으로 변경할 수 있습니다. 전용 그룹에 맞지 않는 모델이 있으면 비활성 모델을 포함해 변경을 거부하므로, 먼저 해당 모델을 다른 공급자 연결로 이동하십시오. 모델 등록과 그룹 변경은 직렬화하며 그룹 변경은 감사 이력에 기록합니다. 이관 전에 백업하십시오.

0028은 관리자 모델 테스트의 사용량을 클라이언트 키 없이 기록할 수 있게 합니다. 테스트는 실제 호출이며 공급자 비용이 발생할 수 있습니다. 마이그레이션 전 백업하십시오.

README의 환경 설정 후 `docker compose up --build -d`와 `docker compose exec backend alembic upgrade head`를 실행합니다. 준비 상태 `/health/ready`는 PostgreSQL 19와 적용된 마이그레이션이 현재 코드의 head에 일치하는지, 암호화 키 형식이 올바른지, 관리자 계정이 없다면 부트스트랩 토큰이 최소 32자인지 확인합니다. 암호화 키가 저장된 모든 키와 일치하는지, 공급자나 IdP가 실제로 동작하는지는 확인하지 않습니다. `/health/live`는 프로세스 생존만 확인합니다. PostgreSQL 19 RC에서 정식 버전으로 옮기기 전에 해당 릴리스의 업그레이드 지침을 확인해야 합니다.

백엔드 이미지는 해시가 포함된 `backend/requirements.txt`로 설치하며 CI에서 `uv.lock`의 운영 의존성과 일치하는지 검사합니다. 의존성을 변경할 때는 `backend`에서 `uv lock` 후 `uv export --locked --no-dev --no-emit-project -o requirements.txt`로 내보내고 `python tests/check_requirements.py`와 테스트를 실행하십시오. `uv` 버전은 CI와 동일한 0.13.7을 사용합니다. 컨테이너에서 `pip check`도 실행하지만 취약점이나 모든 런타임 호환성을 증명하는 검사는 아닙니다.

CI는 `pip-audit`로 고정된 백엔드 운영 의존성을, `npm audit`으로 프런트엔드 개발·운영 의존성을 취약점 데이터베이스와 대조합니다. 검사에는 외부 패키지 및 취약점 서비스 연결이 필요하며 공급자 LLM API는 호출하지 않습니다. 데이터베이스에 알려진 취약점만 확인하므로 이미지 OS 패키지, 알려지지 않은 문제와 운영 환경 검증을 대체하지 않습니다. 2026-11-14 점검에서 `cryptography` 47.0.0의 취약점이 보고되어 50.0.2로 갱신했고 이전 버전으로 만든 모의 암호문의 복호화 및 키 회전 시험을 수행했습니다. 예를 들어 배포된 wheel에 포함된 OpenSSL 관련 문제는 [프로젝트 보안 공지](https://github.com/pyca/cryptography/security/advisories/GHSA-537c-gmf6-5ccf)를 참고하십시오.

백엔드 프로세스와 컨테이너에서 실행하는 마이그레이션·운영 명령은 전용 비관리자 계정 UID 10001로 실행됩니다. 애플리케이션 코드는 해당 계정이 수정할 수 없으며 홈 디렉터리는 쓸 수 있습니다. 운영 환경에서 별도 볼륨을 백엔드에 마운트한다면 필요한 경로에 UID 10001의 접근 권한을 부여하십시오. 이는 컨테이너와 호스트 전반의 보안 설정을 대체하지 않습니다.

백엔드 런타임 연결은 PostgreSQL 잠금 대기 5초, 각 SQL 문 실행 30초, 연결 풀 대기 5초와 신규 연결 3초를 상한으로 사용합니다. 요청 시작 전 DB 제한에 걸리면 공급자에 요청을 보내지 않습니다. 호출 후 완료 기록이 실패하면 미완료 요청이 남을 수 있습니다. Alembic 마이그레이션에는 별도 연결을 사용합니다.

백엔드는 요청 본문을 최대 2 MiB, 읽기 시작 후 전체 60초로 제한하고 초과 시 각각 413 또는 408을 반환합니다. 이 시간에는 공급자 처리 시간이 포함되지 않습니다. 기본 Nginx는 요청 본문을 먼저 버퍼링하므로 클라이언트에서 프록시까지의 전송에는 이 백엔드 제한이 적용되지 않습니다. 제공된 프록시는 헤더 수신 시간과 본문 수신 중 무응답 간격을 각각 15초로 제한합니다. 본문 제한은 **전체 업로드 시간 제한이 아니므로**, 조금씩 지속 전송하는 연결이나 외부 로드밸런서는 배포 환경에서 별도로 제어해야 합니다. HTTP·TLS 프록시의 불완전 요청 시험은 각각 `ha_load.sh`와 `tls_smoke.sh`에서 실행합니다.

모델 조회, 요청 제한과 사용량 기록은 별도 작업 스레드에서 실행합니다. 요청 기록 중 취소되면 트랜잭션 결과를 기다리고 이미 기록된 요청은 `interrupted`로 완료합니다. DB 연결과 스레드 풀은 운영 부하에 맞게 측정해야 합니다.

## TLS 프록시

`deploy/compose.tls.yml`은 프런트엔드 Nginx에서 TLS 1.2/1.3을 종료하고 백엔드 포트는 호스트에 노출하지 않습니다. `.env`에 운영자가 관리하는 전체 인증서 체인과 개인 키의 **절대 경로**를 각각 `MAGPIE_TLS_CERT`, `MAGPIE_TLS_KEY`로 지정한 뒤 `docker compose -f docker-compose.yml -f deploy/compose.tls.yml up --build -d`를 실행합니다. 기본 주소는 `127.0.0.1:8443`이며 선택적으로 `MAGPIE_TLS_BIND`와 `MAGPIE_TLS_PORT`를 설정할 수 있습니다. 외부 접근을 허용하려면 별도의 네트워크 접근 제한과 보안 검토가 필요합니다. 인증서 발급·갱신·만료 감시는 제공하지 않습니다. 인증서 교체 후 프록시 재시작 또는 안전한 reload가 필요하며 개인 키의 파일 권한을 제한하십시오.

이 구성은 보안 헤더와 `no-store`를 적용합니다. 전송 암호화는 클라이언트와 프록시 사이에만 적용되며 프록시·백엔드·PostgreSQL 사이의 Compose 네트워크는 별도 보호가 필요합니다. HSTS 및 추가 인가·방화벽 정책은 실제 도메인과 배포 환경에 맞춰 구성하십시오. `sh backend/tests/tls_smoke.sh`는 테스트 전용 자체 서명 인증서와 별도 Compose 프로젝트, 로컬 포트 18443으로 TLS 및 헤더를 검증하고 이를 정리합니다. 이 인증서는 운영에 사용하지 않습니다.

## 백업과 새 DB 복구

1. `deploy/backup.sh /안전한/경로/magpie.dump`는 커스텀 형식 백업을 생성하고 기존 파일은 덮어쓰지 않습니다. 백업 파일은 비밀 데이터로 관리합니다.
2. `deploy/restore-new.sh /안전한/경로/magpie.dump magpie_restore_01`은 존재하지 않는 새 DB를 만든 후 복원합니다. 기존 DB를 삭제하거나 덮어쓰지 않습니다. 실패하면 새 DB는 조사할 수 있도록 남습니다.
3. 복원 DB를 별도 환경의 `DATABASE_URL`에 연결해 마이그레이션 상태, 계정, 모델 설정을 검증합니다. 공급자 키 복호화에는 백업과 별도로 보관한 동일한 `MAGPIE_ENCRYPTION_KEY`가 필요합니다. 복구 확인 이후 전환은 운영자가 수행합니다.
4. 백업의 읽기 권한, 보관 기간, 외부 저장 위치와 복구 시간 목표는 배포 환경에서 정하고 정기적으로 복구를 연습합니다. `pg_dump`는 PostgreSQL 데이터만 백업하며 `.env`나 암호화 키는 백업하지 않습니다.

`sh backend/tests/backup_restore.sh`는 격리된 DB에서 백업과 복구를 검증합니다. 계정·모델·사용량·감사·암호화된 공급자 키 및 과거 예산 원장의 보존을 확인하며 실제 공급자를 호출하지 않습니다.

PostgreSQL 19 정식 이미지가 제공되면 먼저 `sh backend/tests/postgres_upgrade.sh postgres:19rc2 postgres:19`로 **별도의 두 DB** 사이에서 마이그레이션된 테스트 데이터의 덤프·복원, 애플리케이션 준비 상태와 관리자·모델·키·이력을 검증할 수 있습니다. 두 이미지 인자는 명시적으로 지정하며, 테스트는 임시 볼륨을 정리하고 기존 DB를 수정하지 않습니다. 2026-11-14 격리 시험에서 PostgreSQL 18.7의 테스트 데이터를 19 RC 2에 복구해 검증했으며, CI에도 PostgreSQL 18 → 19 RC 2 경로를 구성했습니다. 실제 RC 2 → 정식 버전 테스트는 정식 이미지가 나온 이후에만 가능합니다. 이 검사는 샘플 데이터의 논리 백업 복원만 다루며 운영 데이터, 확장 기능, 성능, 다운타임 및 정식 업그레이드 지침의 검토를 대신하지 않습니다. [PostgreSQL 19 RC 2 발표와 업그레이드 안내](https://www.postgresql.org/about/news/postgresql-187-1712-1616-1520-1425-and-19-rc-2-released-3442/)를 참고하십시오.

## 제한과 이력

관리·인증 및 모델 API 응답에는 `Cache-Control: no-store`를 설정합니다. 스트리밍 응답에는 기존 `no-cache`도 유지합니다. 발급 직후에만 표시되는 클라이언트 키와 모델 응답을 브라우저나 중간 캐시가 저장하지 않도록 하기 위한 설정입니다.

클라이언트 키 목록의 만료 상태는 목록을 조회한 시점의 PostgreSQL 시계 기준입니다. 만료 시각은 브라우저의 현지 시간으로 표시됩니다. 목록을 연 채로 만료된 경우 목록을 다시 조회해야 표시가 갱신되며, 인증은 요청마다 DB 시계로 만료 여부를 판단합니다.

API 키별 요청 제한은 데이터베이스 시계 기준의 고정 분 단위입니다. 같은 PostgreSQL을 쓰는 여러 인스턴스에서 카운터를 공유하나 경계 시점의 버스트를 허용합니다. 설정을 수정하면 이후 요청부터 반영됩니다. 장애나 재시도 시 공급자에서 처리한 요청을 정확히 한 번만 과금한다는 보장은 없습니다. 백업·복구 시 카운터 상태도 과거 시점으로 복구됩니다.

`GET /v1/models`는 키에 허용된 활성 모델을 보여 줍니다. 키의 복호화 가능성이나 공급자의 실제 유효성·요금·장애는 이 목록으로 확인할 수 없습니다.

공급자 등록 시 `api_key`를 생략하거나 `null`로 지정할 수 있습니다. 모델과 클라이언트 키의 권한은 미리 설정할 수 있지만 공급자 키가 없으면 모델 호출은 503입니다. 관리 화면 또는 `PUT /admin/providers/{id}/key`로 키를 나중에 등록하며, 이 값은 암호화해 저장합니다. 키 등록은 실제 공급자 호출이나 키 유효성 확인을 수행하지 않습니다.

관리자 전용 `GET /admin/provider-credential-health`는 현재 암호화 키로 각 공급자 키를 복호화할 수 있는지 확인합니다. 결과는 복호화 가능·실패·미등록 상태만 포함하며 키와 암호문은 반환하지 않습니다. 검사 시점의 결과이며, 외부 공급자에 접속하거나 공급자 키의 실제 유효성을 검증하지 않습니다. 여러 인스턴스를 사용한다면 각 인스턴스가 동일한 암호화 키를 사용하는지도 별도로 확인하십시오. 이 검사는 `/health/ready`의 자동 검사와 별개입니다.

관리 화면 또는 `DELETE /admin/providers/{id}/key`로 저장된 공급자 키를 제거할 수 있습니다. 연결된 모델의 검증 상태를 미검증으로 전환하고 감사 이력을 기록합니다. 이미 진행 중인 요청은 제거 전 키를 계속 사용할 수 있습니다. Magpie에서 키를 제거해도 공급자 측 키가 폐기되지는 않으므로 유출 시 공급자 측에서도 폐기해야 합니다. 제거 전 백업에도 암호화된 이전 키가 남아 있을 수 있습니다.

클라이언트 키 폐기 또는 모델·공급자 비활성화 이후 시작하는 요청은 허용되지 않습니다. 변경 전 이미 인증과 모델 선택을 통과한 요청은 이전 설정으로 공급자 호출을 완료할 수 있습니다. 격리 PostgreSQL 시험에서 모의 공급자 호출을 진행 중인 상태로 세 가지 변경을 각각 적용하여, 기존 요청은 완료되고 변경 이후 요청은 공급자까지 도달하지 않는 것을 검증합니다.

공급자 요청 시간 제한은 기본 60초이며 `MAGPIE_PROVIDER_TIMEOUT_SECONDS`로 1~3600초를 설정합니다. 응답 전 시간 초과는 504이며 스트리밍 청크 대기 초과는 오류 이벤트로 전달됩니다. 공급자가 이미 처리했을 가능성은 남습니다.

제공된 일반·TLS Nginx 설정의 `/v1/` 응답 읽기 제한은 7500초입니다. 이는 최대 3600초인 공급자 요청과 여유 시간을 고려한 보수적인 값입니다. 별도 로드밸런서, 인그레스 및 클라이언트에도 요청과 스트림에 적합한 제한을 설정해야 합니다. 이 값은 네트워크 무응답이나 처리 시간 전체를 보장하지 않습니다. `MAGPIE_TEST_DELAY_SECONDS=62 sh backend/tests/db_failure.sh`는 별도 테스트 환경에서 62초 동안 지연한 모의 공급자 응답이 일반 프록시를 통과하는지 확인하며, 기본 CI 시험의 지연은 1초입니다.

스트리밍 응답은 관측된 각 `choices` 인덱스가 종료 사유를 보고한 뒤 성공으로 기록합니다. 잘못되거나 미완료된 청크는 오류 이벤트로 처리합니다. 이 검사는 공급자가 아예 보내지 않은 답변이나 모든 공급자 형식을 보증하지 않습니다.

Gemini 네이티브 스트림은 LiteLLM이 잘린 응답에 종료 사유를 만들어낼 수 있어 원본 SSE의 종료 사유를 별도로 확인합니다. 종료 신호가 없거나 확인할 수 없는 경우 완료 대신 오류로 처리합니다. 이 검사는 현재 고정된 LiteLLM의 스트림 인터페이스에 의존하므로 의존성 갱신 시 Anthropic·Gemini 정상 및 절단 스트림의 모의 계약 테스트를 반드시 실행하십시오. 실제 공급자 호환성은 아직 검증하지 않았습니다.

비스트리밍 생성 응답의 선택지와 메시지, 임베딩과 판단 응답의 형식을 검증합니다. 오류 객체나 잘못된 구조가 있으면 502를 반환합니다. 내용의 정확성이나 모든 공급자 형식을 보증하지 않습니다.

스트림 종료 시 사용량은 공급자 스트림 정리 전에 기록합니다. 완료 기록을 기다리는 중 작업이 취소되어도 공급자 스트림 정리를 시도합니다. 정리 작업은 최대 2초 동안 기다리며 실패 시 공급자의 오류 상세를 기록하지 않습니다. 정리 제한은 취소에 응답하는 비동기 어댑터를 전제로 합니다. DB 장애 또는 프로세스 종료 시에는 완료 기록이 남지 않을 수 있으므로 오래된 `started` 요청을 점검해야 합니다.

모델 가격은 생성·임베딩·판단 작업별로 등록하고 해당 작업의 요청에만 적용합니다. 여러 작업을 가진 모델은 가격 등록 시 `operation`을 지정해야 합니다. 단일 작업 모델은 생략 시 그 작업을 사용하고 질문당 가격은 판단 작업에만 허용합니다. 가격 변경은 새 요청에만 적용됩니다.

**0022 마이그레이션의 작업 미지정 토큰 가격은 이력으로 보존되며 새 요청에 적용되지 않습니다.** 필요한 작업별 가격을 다시 등록하십시오. 가격이 없으면 비용은 미확인입니다. 기존 요청의 가격 ID와 추정 비용은 유지합니다.

인증된 관리 API 요청이 입력 검증, 충돌 또는 서버 오류로 실패하면 관리자 식별자, 서버에 정의된 경로 형식, HTTP 메서드와 상태 코드를 감사합니다. 요청 본문, 쿼리 문자열, 실제 경로의 식별자 및 오류 상세는 기록하지 않습니다. 실패 감사는 별도의 트랜잭션으로 기록되며 DB 장애 시에는 기록이 누락될 수 있습니다. 인증되지 않은 임의의 관리 요청은 감사 쓰기 폭주를 막기 위해 여기서 기록하지 않으며 로그인 실패는 별도로 제한·기록합니다. 접근 프록시에서 인증 실패와 DB 장애를 모니터링하십시오.

처리되지 않은 HTTP 예외와 사용량 확정 실패는 애플리케이션 로그에 일반 오류 메시지만 남깁니다. 예외 상세에는 요청 값이나 자격 증명이 포함될 수 있어 추적을 출력하지 않습니다. 응답이 시작된 뒤 발생한 처리되지 않은 오류는 기존 HTTP 상태를 바꿀 수 없으며 연결이 불완전하게 종료될 수 있습니다. 원인 분석은 비밀을 제거한 격리 환경에서 재현하십시오. 별도로 구성한 프록시·인프라와 외부 라이브러리의 로그 정책도 운영자가 확인해야 합니다.

`docker compose exec backend python -m app.maintenance`는 2일 이상 지난 제한 카운터와 만료된 세션을 지웁니다. 정기 실행은 운영 환경에서 구성하십시오. 요청·감사 이력은 관리자 API의 `/admin/retention/preview`와 `/admin/retention/apply`로 미리 확인해 수동 정리할 수 있습니다. 요청 본문이나 공급자 API 키를 로그에 넣지 않습니다.

`GET /admin/operational-status`는 DB 크기와 오래된 `started` 요청 수를 보여 줍니다. `PUT /admin/operational-policy`로 경고 기준을 지정할 수 있습니다. 별도 모니터링과 보존 정책이 필요합니다.

요청 시도와 감사 이력은 이전 항목을 추가로 조회할 수 있습니다. 요청 목록은 `before_started_at`과 `before_request_id`를 함께, 감사 이력은 `before_id`를 사용합니다. 각 페이지는 고정 스냅샷이 아닙니다.

관리 화면의 사용량 필터는 늦게 도착한 이전 응답이 최신 결과를 덮어쓰지 않습니다. 집계와 목록은 별도 조회이므로 동일 DB 스냅샷이 아닙니다.

## 관리자 복구

SSO 인증은 제거되었습니다. 기존 SSO 연결과 세션 기록은 보존하지만 SSO 세션은 더 이상 인증에 사용할 수 없습니다. 기존 콜백 주소는 410을 반환하며 쿼리를 접근 로그에 기록하지 않습니다. 계정 비밀번호로 로그인하거나 아래 복구 절차를 사용하십시오.

첫 계정 등록 후 부트스트랩 토큰은 사용할 수 없습니다. 계정 로그인이 되는 것을 확인한 다음 `.env`에서 `MAGPIE_ADMIN_TOKEN`을 비우고 백엔드 인스턴스를 재생성할 수 있습니다. 새 DB에 관리자 계정이 없다면 32~512자의 토큰이 필요하며, 없으면 준비 상태가 실패하고 최초 계정을 생성할 수 없습니다. 관리자 비밀번호 재설정은 다른 활성 관리자 세션을 사용하며 대상 계정의 모든 세션을 폐기합니다. 마지막 활성 관리자는 비활성화할 수 없습니다. 관리자 활성 상태 변경은 PostgreSQL의 공유 잠금으로 직렬화하며, 통합 시험에서 두 DB 세션이 동시에 마지막 두 계정을 비활성화하려 할 때 한 계정이 활성 상태로 남는지 확인합니다. `sh backend/tests/bootstrap_retire.sh`는 격리된 DB에서 토큰 미설정·최초 계정 생성·토큰 제거 후 로그인을 검증합니다.

비밀번호 로그인 시에는 검증 후 관리자 계정의 현재 해시와 활성 상태를 잠금 아래 다시 확인해 비밀번호 재설정이나 계정 비활성화와 겹친 오래된 로그인으로 새 세션이 남지 않도록 합니다. 이미 처리 중인 관리 요청까지 취소하지는 않습니다.

관리 화면은 로그아웃하거나 다른 인증을 시작할 때 진행 중인 화면 요청의 응답을 취소하고 편집·키 표시 상태를 지웁니다. 토큰 입력란은 연결하기 전에는 현재 인증에 사용되지 않습니다. 클라이언트가 요청을 취소해도 서버에 이미 도착한 관리 작업은 완료될 수 있습니다. 키 발급 중에는 화면이 중복 제출을 막고, 응답 오류 시 결과를 확인할 수 없다는 안내를 표시합니다. 특히 키 발급 중 로그아웃하거나 통신이 끊기면 발급 결과를 받지 못할 수 있으므로 키 목록을 확인하고 필요하면 해당 키를 폐기하십시오. 관리 화면은 결과 미확인 시 키 목록을 새로 조회하고 같은 입력의 재시도에는 동일한 요청 식별자를 사용합니다. 목록을 확인한 뒤 별도의 새 발급을 원하면 확인 대화상자를 거쳐 새 요청을 준비하고 다시 발급 버튼을 누릅니다. 관리 API의 `POST /admin/api-keys`에 선택적 `Idempotency-Key` 헤더(영문·숫자·밑줄·하이픈 16~128자)를 보내면, 같은 식별자의 동시 요청과 재시도에서 최대 한 개의 키만 발급됩니다. 식별자 해시만 DB에 보관하고 이미 처리된 식별자는 입력 내용과 무관하게 409로 거부합니다. 최초 응답을 잃었으면 키 원문을 복구할 수 없으므로 목록에서 해당 키를 확인해 폐기하고 새 식별자로 재발급하십시오. 식별자를 보내지 않거나 다른 식별자를 쓰는 요청은 중복 제거하지 않으며, 화면 새로고침 후에는 이전 식별자를 보관하지 않습니다.

공급자 등록·그룹 변경·공급자 키 변경, 모델 등록·수정, 클라이언트 키 발급·권한 변경은 화면에서 60초 동안 응답을 기다립니다. 시간 초과나 통신 장애는 서버의 작업 취소를 보장하지 않습니다. 공급자와 모델 설정, 키 권한은 새로고침 후 목록과 감사 이력을 확인하고, 공급자 키 원문은 다시 표시할 수 없으므로 변경 결과를 감사 이력에서 확인하십시오. 키 발급의 결과 미확인 처리는 위 절차를 따릅니다.

클라이언트 키 원문은 발급 서랍을 닫기 전에 복사하십시오. 서랍을 닫으면 화면 메모리에서도 원문을 지우며 다시 표시할 수 없습니다. 응답을 받지 못한 발급 요청의 중복 방지 식별자는 서랍을 닫아도 현재 세션 동안 유지됩니다.

발급 결과가 미확인인 동안에는 같은 내용의 재시도만 가능합니다. 키 목록과 감사 이력을 확인하고 새 발급 요청을 준비해야 이름·모델·제한을 바꿀 수 있습니다.

관리 화면의 시간은 브라우저 현지 시간으로 `YYYY-MM-DD:HHmm` 형식을 사용합니다. 조회 기간과 키 만료 시각은 직접 입력하거나 옆의 날짜·시간 선택기를 사용할 수 있으며 서버에는 UTC 시각으로 전달합니다. 사용량 조회는 시작 시각을 포함하고 종료 시각은 포함하지 않습니다. 이력의 초 단위는 화면에서 표시하지 않지만 원본과 페이지네이션에는 그대로 유지합니다. 키를 수정할 때 만료 시각을 변경하지 않으면 표시되지 않은 초와 원래 UTC 시각도 유지합니다.

관리자 세션 로그아웃 시 서버 폐기 응답을 5초 안에 확인하지 못하면 화면에 경고를 표시합니다. 이때 브라우저의 토큰은 지워지지만 서버 세션은 만료될 때까지 유효할 수 있습니다. 다시 로그인해 해당 계정의 비밀번호를 변경하면 기존 세션이 폐기됩니다. 401을 포함한 오류는 폐기 성공을 확인할 수 없으므로 경고하며, 이미 만료된 세션에도 경고가 표시될 수 있습니다. 부트스트랩 토큰은 이 엔드포인트에서 폐기할 수 없으며 첫 계정 생성으로 비활성화됩니다.

모든 관리자 자격 증명을 잃은 경우 서버와 DB에 접근할 수 있는 운영자는 **모든 게이트웨이 인스턴스를 중지한 후** `docker compose run --rm --no-deps backend python -m app.recover_admin 관리자계정`을 대화형 터미널에서 실행할 수 있습니다. DB는 실행 중이어야 합니다. 기존 계정만 복구할 수 있으며 새 비밀번호를 두 번 입력합니다. 이 명령은 계정을 활성화하고 해당 계정의 기존 세션을 폐기하며 `operator`의 `admin.recover` 감사 이력을 같은 트랜잭션으로 기록합니다. 비밀번호는 명령행 인자나 환경 변수로 전달하지 않습니다. 작업 완료 후 게이트웨이를 재시작하고 새 비밀번호로 로그인하십시오. 서버·DB 접근 권한은 관리자 복구 권한을 포함하므로 엄격히 제한해야 합니다.

## 공급자 비밀값 암호화 키 교체

1. DB와 기존 암호화 키를 백업하고 복구 가능성을 확인합니다.
2. **모든 Magpie 백엔드 인스턴스를 중지**합니다. 실행 중인 인스턴스가 구 키로 새 비밀값을 저장하면 데이터가 혼합되므로 중지는 필수입니다.
3. 안전한 비밀 주입 수단으로 `MAGPIE_OLD_ENCRYPTION_KEY`, `MAGPIE_NEW_ENCRYPTION_KEY`를 임시 실행 컨테이너에 전달하고 `python -m app.rotate_key`를 실행합니다. 저장된 공급자 키와 기존에 저장된 만료되지 않은 미사용 SSO 검증값을 같은 트랜잭션에서 다시 암호화합니다. 대상 값이 하나라도 복호화되지 않으면 DB 변경을 롤백합니다. 이미 사용했거나 만료된 SSO 트랜잭션은 회전하지 않으며, 출력에는 키가 나타나지 않습니다.
4. 성공한 경우에만 배포 환경의 `MAGPIE_ENCRYPTION_KEY`를 새 값으로 교체하고 백엔드를 시작합니다. 임시 비밀값을 제거하고 안전한 백업을 유지합니다.

회전 도중 장애가 발생하면 재시도 전에 DB 트랜잭션 결과와 실제 키 버전을 운영자가 확인해야 합니다. 실행 중인 인스턴스와 동시에 회전하는 것은 지원하지 않습니다.

## 사용자 정의 공급자

Z.AI 글로벌과 Zhipu 중국 Coding Plan 프리셋은 각각 구독 전용 OpenAI Chat Completions 주소와 별도 키를 사용하며 생성 작업만 등록할 수 있습니다. 공식 문서는 해당 구독을 지정된 도구·제품 환경에서만 사용할 수 있다고 명시하며 Magpie 경유를 허용하는지는 확인되지 않았습니다. 운영자는 사용 전에 공급자에게 허용 여부를 확인해야 합니다. 일반 API와 키를 혼용하지 마십시오. [글로벌 사용 범위와 주소](https://docs.z.ai/devpack/tool/others), [중국 사용 범위와 주소](https://docs.bigmodel.cn/cn/coding-plan/tool/others)를 참고하십시오. 실제 공급자 호출로 검증하지 않았습니다.

Kimi Code 글로벌·중국 프리셋은 별도의 구독용 키와 OpenAI 호환 Chat Completions 주소를 사용합니다. Magpie에서는 생성 작업만 등록할 수 있으며, 운영자는 사용하려는 코딩 도구와 계정이 해당 구독의 이용 조건에 맞는지 확인해야 합니다. 일반 Moonshot API 키와 주소는 별도입니다. [Kimi Code 공식 문서](https://www.kimi.com/code/docs/en/)에 따르면 구독은 프로그래밍 시나리오를 위한 것이며 제품 통합에는 Kimi Platform을 안내합니다. 실제 공급자 호환성은 검증하지 않았습니다.

공급자 선택에는 Moonshot 글로벌·중국, Alibaba/Qwen 싱가포르·베이징, SiliconFlow 글로벌·중국, MiniMax 글로벌·중국을 위한 고정 엔드포인트와 Novita·Chutes·Synthetic의 LiteLLM 프리셋이 있습니다. 지역별 키와 모델 가용성은 서로 다를 수 있으며 코딩 전용 요금제는 별도 주소나 계약이 필요할 수 있습니다. 등록 화면에서 고정 주소를 확인하고 해당 공급자 문서와 계정의 지역·요금제를 확인하십시오. 워크스페이스 전용 주소나 다른 지역은 아래 사용자 정의 허용 목록으로 등록할 수 있습니다. [Alibaba Model Studio 지역별 주소](https://www.alibabacloud.com/help/en/model-studio/base-url), [Moonshot 공식 설정](https://github.com/MoonshotAI/kimi-code/blob/main/docs/en/configuration/providers.md), [SiliconFlow 호환 API](https://docs.siliconflow.cn/docs/userguide/quickstart), [LiteLLM 공급자 목록](https://docs.litellm.ai/docs/providers/)을 참조하십시오. 실제 공급자 API 호출은 검증하지 않았습니다.

Gemini 임베딩은 원본 `usageMetadata.promptTokenCount`를 확인해 보고된 경우에만 기록합니다. 없거나 불명확한 값은 미확인으로 남기며, 숫자 벡터는 요청 시 Base64로 변환합니다. LiteLLM 갱신 시 모의 계약 시험이 필요합니다.

생성 응답과 스트림은 공급자가 명시한 사용량만 가능한 범위에서 기록합니다. 값의 출처나 가격 대응이 불명확한 항목은 미확인으로 남기며, 프롬프트·응답·헤더를 저장하지 않습니다. LiteLLM 갱신 시 모의 계약 시험을 실행해야 합니다.

OpenAI 호환 임베딩은 변환 전 응답의 입력 토큰을 요청별로 확인하여 명시적인 0을 기록합니다. 응답에 해당 값이 없거나 확인 경로가 동작하지 않으면 미확인으로 처리합니다. OpenAI 호환 생성·임베딩에서 변환 전 콜백으로 확인한 HTTP 200 응답에 오류가 포함된 경우 실패로 처리합니다. 이 확인은 고정된 LiteLLM의 요청별 로깅 인터페이스에 의존하므로 갱신 시 모의 계약 시험이 필요합니다. Gemini 외 다른 비 OpenAI 호환 어댑터에서는 입력 토큰 0을 누락과 구분하지 못해 미확인으로 처리합니다. 캐시 관련 수치로 기본 입력량이 불명확한 경우에는 추정 비용을 기록하지 않습니다.

TypeSafe와 OpenAI 판단 응답은 LiteLLM이 누락된 사용량을 0으로 채우기 전에 요청별 원본에서 확인한 입력·출력 토큰만 기록합니다. 명시적으로 보고된 0은 0으로 기록하고 누락이나 유효하지 않은 값은 미확인으로 처리합니다. 캐시 또는 추론 토큰이 있는 차원은 가격 계산의 의미가 불명확하므로 미확인으로 취급합니다. 미확인 항목에 0이 아닌 토큰 가격이 설정되어 있으면 추정 비용을 기록하지 않습니다. 질문 수 기준 가격은 요청의 질문 수로 계산합니다. HTTP 오류 상태 또는 오류 본문은 판단 성공으로 처리하지 않습니다. 이 경로는 LiteLLM 1.109.1 내부 인터페이스를 사용하므로 버전 갱신 시 공급자 변환과 사용량 검증 테스트를 함께 수행해야 합니다.

공급자 토큰 수가 음수, 정수가 아닌 값, PostgreSQL 정수 범위 초과이거나 같은 항목의 별칭 값이 서로 다르면 사용량 전체를 미확인으로 기록합니다. 합계가 알려진 입력과 출력의 합보다 작은 경우에도 동일하게 처리합니다. 토큰 기준 추정 비용은 미확인으로 기록합니다. 질문 수 기준 비용은 요청한 질문 수를 기준으로 계산합니다. 클라이언트에 전달된 공급자 응답의 사용량은 이 기록 규칙과 별개입니다.

Gemini 임베딩 어댑터는 `files/`, Google Files API 주소, `gs://` 및 base64 데이터 URL을 일반 텍스트가 아닌 파일·미디어로 해석할 수 있습니다. Magpie는 해당 입력과 토큰 배열을 Gemini 모델에 전달하기 전에 거부합니다. Gemini에서 이런 접두사 자체를 텍스트로 임베딩해야 한다면 별도의 표현으로 입력해야 합니다.

Venice AI의 고정 주소는 [공식 Chat Completions API](https://docs.venice.ai/api-reference/endpoint/chat/completions)를 기준으로 등록되어 있습니다. Z.AI Coding Plan 등 특정 도구 전용 요금제는 공급자 이용 조건과 Magpie 지원 여부가 확인되지 않아 별도 프리셋으로 제공하지 않습니다. [Z.AI의 공식 지원 환경 조건](https://docs.z.ai/devpack/tool/others)을 확인하십시오.

생성형 요청은 일반 함수 호출만 전달하며 MCP, 웹 검색 등 공급자 실행 도구 유형은 거부합니다. 일부 공급자는 자체 MCP 도구를 제공하므로 이 제한은 사용자가 지정한 도구가 외부에서 자동 실행되는 것을 방지합니다. [Z.AI MCP 호출](https://docs.z.ai/guides/capabilities/mcp-call)을 참고하십시오.

생성형 스트림은 공급자의 종료 신호를 확인한 뒤 `[DONE]`을 전달합니다. 미완료·잘못된 청크·공급자 오류는 오류로 기록합니다. 원본 스트림 인터페이스에 의존하므로 의존성 갱신 시 모의 계약 시험이 필요하며 모든 공급자와의 호환성을 보장하지 않습니다.

`MAGPIE_ALLOWED_PROVIDER_BASES`에 신뢰할 수 있는 HTTPS 기본 URL을 쉼표로 구분해 사전 등록해야 관리자가 그 주소를 공급자 연결에 사용할 수 있습니다. localhost·비공인 IP 직접 지정, URL 자격 증명과 쿼리 문자열을 차단하고 요청 시에도 허용 목록을 다시 확인합니다. 이 검사는 DNS 변경이나 DNS 리바인딩을 완전히 방지하지 못하므로 운영 환경에서는 별도의 네트워크 egress 정책으로 내부·메타데이터 주소 접근을 차단해야 합니다. 공급자 주소 변경 또는 허용 목록 해제 시 기존 연결도 영향을 받습니다.

생성형 메시지의 콘텐츠는 텍스트와 Base64 데이터 URL 이미지(PNG·JPEG·WebP·GIF)만 허용합니다. LiteLLM의 일부 공급자 어댑터가 이미지나 파일 URL을 게이트웨이 서버에서 직접 가져올 수 있으므로, 원격 미디어 URL과 파일·오디오 등 다른 콘텐츠 유형은 거부합니다. 일반 텍스트 안의 URL은 그대로 사용할 수 있습니다. 함수 호출 메시지와 도구 정의는 전달할 수 있으나 Magpie가 도구를 실행하지는 않습니다. 이미지 포맷의 완전성과 공급자별 지원 여부는 공급자에서 검증하며, 게이트웨이 요청 전체 크기는 2 MiB로 제한됩니다.

생성형 요청은 `max_tokens` 또는 `max_completion_tokens` 중 하나와 assistant 메시지의 `reasoning_content`를 전달할 수 있습니다. `temperature`와 `top_p`는 유한한 JSON 숫자만 허용하며 문자열·불리언·NaN·무한대는 공급자 호출 전에 거부합니다. 파라미터와 추론 이력의 실제 지원은 모델과 공급자마다 다르며 등록만으로 검증되지는 않습니다. 예를 들어 [MiniMax의 OpenAI 호환 API 안내](https://platform.minimax.io/docs/api-reference/text-openai-api)는 함수 호출 대화에서 추론 이력을 유지하도록 설명합니다.

## 예산 기능 제거와 기존 데이터

예산·정산 API와 신규 예약은 제거했습니다. 기존 `key_budgets`, `budget_reservations`, `budget_adjustments`와 연결된 사용량 이력은 삭제하지 않습니다. 보존된 예산이 있는 키는 기존 한도가 무제한으로 바뀌지 않도록 API 호출을 거부합니다. 관리자 화면에서 해당 키를 확인하고 새 키를 발급해 클라이언트에 교체한 뒤 기존 키를 폐기하십시오. 원장은 백업 또는 DB 조회로 보관하며 새 요청은 예산을 적용하지 않습니다. 공급자 요금 및 한도 관리는 공급자 측에서 수행해야 합니다.

## 이력 보존

관리 API `POST /admin/retention/preview`와 `POST /admin/retention/apply`로 보존 기간을 지정해 삭제 대상 건수를 미리 확인한 뒤 수동으로 이력을 삭제할 수 있습니다. 삭제 건수는 미리보기 이후의 요청에 따라 바뀔 수 있습니다. 진행 중·미완료 요청과 예산 원장에 연결된 요청은 삭제하지 않습니다. 이 작업은 영구적이므로 실행 전 보관 정책과 백업을 확인하십시오. 이력 삭제 자체는 감사 이력에 남습니다.

## 여러 백엔드 인스턴스

`docker compose -f docker-compose.yml -f deploy/compose.ha.yml up --build -d`는 백엔드 2개를 동일 PostgreSQL에 연결하며 외부에는 프런트엔드 포트만 노출합니다. DB 자체는 단일 인스턴스이므로 이 구성만으로 DB 고가용성이 제공되지는 않습니다. 마이그레이션은 한 번만 수행하고 모든 인스턴스에 같은 암호화 키를 전달해야 합니다. 프록시는 Docker DNS를 주기적으로 다시 조회하지만 DNS가 건강 상태를 반영하지는 않습니다. 실제 배포에서는 준비 상태 확인과 인스턴스 교체, DB 장애 복구 및 연결 풀 한도를 오케스트레이터에서 관리해야 합니다.

## 동시 요청 검증

`docker compose exec -T backend python - < backend/tests/load_smoke.py`는 임시 PostgreSQL DB에서 모의 동시 요청·요청 제한·사용량을 확인합니다. `sh backend/tests/ha_load.sh`는 격리된 두 백엔드와 프록시에서 동일한 작업과 공유 제한을 검증합니다. 실제 공급자 호출은 하지 않습니다.

`MAGPIE_SOAK_SECONDS`와 `MAGPIE_HA_SOAK_SECONDS`로 모의 지속 부하의 시간을 지정할 수 있습니다(0~3600초). 이 시험은 실제 공급자나 장시간 운영 검증을 대신하지 않습니다.

2026-11-14의 PostgreSQL 19 RC 모의 부하 관측은 해당 환경의 단기 결과이며 운영 처리량이나 장시간 안정성을 보증하지 않습니다.

`sh backend/tests/db_failure.sh`는 격리된 PostgreSQL과 두 백엔드에서 DB 중단·복구와 처리 중 프로세스 종료를 시험합니다. DB 장애 시 새 요청은 공급자에 전달되지 않으며, 완료 기록이 없으면 요청 상태는 `started`로 남을 수 있습니다. 실제 공급자 처리 여부는 운영자가 확인해야 합니다.

## 모델 호출 및 사용량

모델 별칭으로 직접 호출합니다. 라우팅과 자동 재시도는 제공하지 않습니다. 기존 라우트와 상태는 데이터베이스에 보존되지만 동작하지 않으며 관리 API에서도 제공하지 않습니다. 기존 별칭과 같은 이름의 모델을 새로 등록하면 해당 모델을 직접 호출합니다.

관리 현황의 `unique_requests`는 선택한 필터에 일치하는 시도들의 전체 요청 ID를 중복 제거한 수이고 `attempts`, 성공·실패 수와 지연은 공급자 시도 기준입니다. 기존 API의 `requests`는 호환성을 위해 시도 수로 유지합니다. 모델·상태·시간 필터는 먼저 각 시도에 적용되므로, 필터별 고유 요청 수를 더해 전체 고유 요청 수를 계산할 수는 없습니다. 요청 이력 API의 `root_request_id` 필터 또는 관리 화면의 요청 ID 검색으로 관련 시도를 찾을 수 있습니다. 보존 정책으로 삭제된 시도나 공급자 호출 전 거부된 요청은 이 집계에 포함되지 않습니다.

모델에 임베딩 배치 지원 여부와 최대 항목 수를 선택적으로 등록할 수 있습니다. 미지원 또는 최대치를 초과하는 배치는 공급자 호출 전에 거부합니다. 미확인은 지원한다고 보증하는 값이 아니라 사전 제한을 적용하지 않는 값입니다. 최대 입력 토큰 수는 정수 토큰 배열에는 적용되지만, 문자열은 공급자별 토크나이저가 다르므로 사전에 토큰 수를 계산하지 않습니다. 등록한 값이 실제 공급자에서 지원되는지는 운영자가 검증해야 합니다.

임베딩 입력은 빈 문자열·빈 배열을 허용하지 않으며 토큰 배열은 음수가 아닌 정수만 받습니다. 불리언과 소수를 정수로 자동 변환하지 않습니다. 배치에 빈 텍스트나 빈 토큰 배열이 포함된 경우에도 공급자 호출 전 400을 반환합니다.

임베딩 응답은 요청한 `encoding_format`에 맞춥니다. Base64는 리틀엔디언 IEEE 754 float32이며 잘못된 인코딩이나 유한하지 않은 값은 거부합니다.

등록된 임베딩 차원과 요청의 `dimensions`가 모두 있으면 일치해야 합니다. 응답의 벡터 개수·인덱스·차원·수치를 검증하며 실패 시 502와 오류 이력을 남깁니다. 차원이 같아도 벡터 공간의 동일성은 보장되지 않습니다.

관리 화면은 공급자나 모델의 검증 상태를 표시하거나 검증을 요구하지 않습니다. 기존 관리자 API로 기록한 모델별 검증 상태와 이력은 호환성을 위해 유지됩니다. 이는 **운영자의 기록**이며 Magpie가 자동으로 외부 API를 호출하거나 검증 사실을 보증하지 않습니다. 근거에는 API 키, 요청 본문이나 개인 정보를 입력하지 마십시오. 공급자·모델 ID 또는 관련 기능 설정을 변경하면 해당 검증 상태가 미검증으로 초기화되고 이력이 남습니다. 공급자 API 키 교체 시에도 해당 연결의 모든 모델 검증 상태가 초기화되며, 설정 변경과 동시에 오래된 버전을 기준으로 검증 기록을 저장하려 하면 거부됩니다. 검증 상태는 요청을 자동 차단하지 않습니다.

## TypeSafe 이미지 판단

`/v1/decisions`는 기존 문자열 입력 외에 사용자 메시지와 `input_text`, `input_image` 콘텐츠 배열을 받습니다. TypeSafe와 OpenAI 연결에서 판단형을 등록할 수 있으며 모델별 실제 지원 여부는 운영자가 확인해야 합니다. 이미지는 `data:image/png;base64,...` 또는 `data:image/jpeg;base64,...` 형식만 허용합니다. 외부 URL은 가져오지 않습니다. TypeSafe 이미지 또는 `box` 질문에는 요청 헤더 `TypeSafe-Danger-Zone-Images: true`가 필요합니다. `box`는 이를 지원하는 TypeSafe 모델에서만 사용합니다. OpenAI 이미지 판단에는 이 헤더가 필요하지 않습니다. TypeSafe는 이미지와 Box 기능을 실험적으로 분류하며 모델별 지원과 이미지 크기·해상도 제약은 공급자가 결정합니다. Magpie 전체 요청 크기 제한은 2 MiB이므로 공급자 제한보다 작습니다. 요청 본문과 이미지 데이터는 사용량·감사 이력에 저장하지 않습니다. [TypeSafe 이미지 문서](https://docs.typesafe.ai/images)와 [OpenAI 판단 API 문서](https://developers.openai.com/api/docs/guides/decisions)를 참고하십시오. 실제 공급자와의 호환성은 검증하지 않았습니다.

판단 응답의 질문 이름·유형·확률·선택 항목·점수와 Box 좌표를 검증합니다. 잘못된 응답은 502입니다. 실제 업무 데이터로 판단 품질을 평가해야 합니다.


`sh backend/tests/provider_stall.sh`는 격리 환경에서 모의 공급자의 응답 지연·스트림 정리·후속 요청과 중복 키 발급 방지를 확인합니다. 실제 공급자 네트워크는 호출하지 않습니다.

Magpie는 LiteLLM의 `LITELLM_OFFLINE_MODE=true`를 강제해 외부 카탈로그나 토크나이저의 자동 다운로드를 방지합니다. 명시적인 공급자 API 호출은 차단하지 않으며 출처가 불명확한 스트림 사용량은 기록하지 않습니다.
